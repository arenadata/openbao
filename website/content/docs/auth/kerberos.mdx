# Kerberos auth method

The `kerberos` auth method provides an automated mechanism to retrieve
an OpenBao token for Kerberos entities.

[Kerberos](https://web.mit.edu/kerberos/) is a network authentication
protocol invented by MIT in the 1980s. Its name is inspired by Cerberus,
the three-headed hound of Hades from Greek mythology. The three heads
refer to Kerberos' three entities - an authentication server, a ticket
granting server, and a principals database. Kerberos underlies
authentication in Active Directory, and its purpose is to _distribute_
a network's authentication workload.

OpenBao's Kerberos auth method was originally written by the folks at
[Winton](https://github.com/wintoncode), to whom we owe a special thanks
for both originally building the plugin, and for collaborating to bring
it into HashiCorp's maintenance.

## Prerequisites

Kerberos is a very hands-on auth method. Other auth methods like
[LDAP](ldap.mdx) only require
a cursory amount of knowledge for configuration and use.
Kerberos, on the other hand, is best used by people already familiar
with it. We recommend that you use simpler authentication methods if
your use case is achievable through them. If not, we recommend that
before approaching Kerberos, you become familiar with its fundamentals.

- [MicroNugget: How Kerberos Works in Windows Active Directory](https://www.youtube.com/watch?v=kp5d8Yv3-0c)
- [MIT's Kerberos Documentation](https://web.mit.edu/kerberos/)
- [Kerberos: The Definitive Guide](https://www.amazon.com/Kerberos-Definitive-Guide-ebook-dp-B004P1J81C/dp/B004P1J81C/ref=mt_kindle?_encoding=UTF8&me=&qid=1573685442)

Regardless of how you gain your knowledge, before using this auth method,
ensure you are comfortable with Kerberos' high-level architecture, and
ensure you've gone through the exercise of:

- Creating a valid `krb5.conf` file
- Creating a valid `keytab` file
- Authenticating to your domain server with your `keytab` file using `kinit`

With that knowledge in hand, and with an environment that's already tested
and confirmed working, you will be ready to use Kerberos with OpenBao.

## Configuration

- Enable Kerberos authentication in OpenBao:

```shell-session
$ bao auth enable \
    -passthrough-request-headers=Authorization \
    -allowed-response-headers=www-authenticate \
    kerberos
```

- Create a `keytab` for the Kerberos plugin (this keytab is used by the OpenBao server itself, another keytab should be generated for login purposes):

```shell-session
$ ktutil
ktutil:  addent -password -p your_service_account@REALM.COM -e aes256-cts -k 1
Password for your_service_account@REALM.COM:
ktutil:  list -e
slot KVNO Principal
---- ---- ---------------------------------------------------------------------
  1    1            your_service_account@REALM.COM (aes256-cts-hmac-sha1-96)
ktutil:  wkt openbao.keytab
```

The KVNO (`-k 1`) should match the KVNO of the service account. An error will show in the OpenBao logs if this is incorrect.

Different encryption types can also be added to the `keytab`, for example `-e rc4-hmac` with additional `addent` commands.

Then base64 encode it:

```shell-session
$ base64 openbao.keytab > openbao.keytab.base64
```

- Configure the Kerberos auth method with the `keytab` and
  entry name that will be used to verify inbound login
  requests:

```shell-session
$ bao write auth/kerberos/config \
    keytab=@openbao.keytab.base64 \
    service_account="openbao_svc"
```

- Configure the Kerberos auth method to communicate with
  LDAP using the service account configured above. This is
  a sample LDAP configuration. Yours will vary. Ensure you've
  first tested your configuration from the OpenBao server using
  a tool like `ldapsearch`.

```shell-session
$ bao write auth/kerberos/config/ldap \
    binddn=openbao_svc@MATRIX.LAN \
    bindpass=$OPENBAO_SVC_PASSWORD \
    groupattr=sAMAccountName \
    groupdn="DC=MATRIX,DC=LAN" \
    groupfilter="(&(objectClass=group)(member:1.2.840.113556.1.4.1941:={{.UserDN}}))" \
    userdn="CN=Users,DC=MATRIX,DC=LAN" \
    userattr=sAMAccountName \
    upndomain=MATRIX.LAN \
    url=ldaps://somewhere.foo
```

The LDAP above relies upon the same code as the LDAP auth method.
See [its documentation](ldap.mdx)
for further discussion of available parameters.

- Configure the OpenBao policies that should be granted to those
  who successfully authenticate based on their LDAP group membership.
  Since this is identical to the LDAP auth method, see
  [Group Membership Resolution](ldap.mdx#group-membership-resolution)
  and [LDAP Group -> Policy Mapping](ldap.mdx#ldap-group---policy-mapping)
  for further discussion.

```shell-session
$ bao write auth/kerberos/groups/engineering-team \
    policies=engineers
```

The above group grants the "engineers" policy to those who authenticate
via Kerberos and are found to be members of the "engineering-team" LDAP
group.

## Configuration without LDAP

When the entities logging in are service principals rather than directory
users, LDAP adds nothing: Kerberos already proves the principal name. In that
case skip `config/ldap` and bind principals to policies directly with roles.
Roles are consulted only while `config/ldap` is not set; writing an LDAP
configuration switches the mount to group based resolution, deleting it
(`bao delete auth/kerberos/config/ldap`) switches back.

```shell-session
$ bao write auth/kerberos/roles/hadoop \
    bound_principals="hadoop/*@MATRIX.LAN,nn/*@MATRIX.LAN" \
    token_policies=hadoop-keys \
    token_ttl=1h
```

- `bound_principals` is a comma-separated list of patterns matched against the
  full principal name, `primary/instance@REALM`. `*` matches any characters,
  including `/` and `@`; everything else is compared literally and
  case-sensitively. At least one entry is required.
- The usual [token parameters](/api-docs/auth/kerberos#createupdate-role)
  (`token_policies`, `token_ttl`, `token_bound_cidrs`, ...) are available on
  the role.

At login the authenticated principal is matched against every role, or only
against the role named by the `role` parameter. Exactly one role must match:
no match, or several matches without a `role`, returns a 403 naming the
candidates. The token carries that role's policies and parameters, the
`role` metadata field names it, and `token_bound_cidrs` of the role is
enforced at login. The entity alias is the full principal, so the same name
in two realms stays two identities. Tokens issued from roles are renewable
as long as the role still exists and still binds the principal.
`remove_instance_name` does not affect matching: patterns always see the full
principal.

The `service_account` in `config` still has to own the service principal the
client asks a ticket for (usually `HTTP/<openbao-host>`), and the keytab has
to hold that account's key with the current KVNO.

## Delegation tokens

Processes started by a Kerberos-authenticated job often have no Kerberos
credentials of their own: YARN containers, Spark executors, Tez tasks. Hadoop
solves this with delegation tokens, and the auth method can issue them: a
principal that authenticates with SPNEGO obtains a token, hands it to those
processes through the Hadoop `Credentials` machinery, and they log in to
OpenBao with the token alone. The token is byte-compatible with Hadoop's
`AbstractDelegationTokenIdentifier` and `Token`, so `Token.decodeIdentifier()`,
credential files, the YARN `TokenRenewer` service and Spark's delegation token
framework handle it without conversion.

Delegation tokens require the roles configuration above and are enabled by
writing `config/delegation`; every parameter has a default:

```shell-session
$ bao write auth/kerberos/config/delegation \
    renew_interval=24h \
    max_lifetime=168h \
    key_rotation_interval=24h \
    cleanup_interval=1h \
    token_kind=OPENBAO_DELEGATION_TOKEN
```

A token has two lifetimes, as in Hadoop: an `expiry` that a renewal pushes
forward by `renew_interval`, and a `max_date`, `max_lifetime` after issuance,
that nothing extends. `token_kind` is written into every token and must match
the kind of the `TokenIdentifier` class on the Hadoop side.

The endpoints under `delegation/` take the same `Authorization: Negotiate`
header as `login`; a delegation token can never be used to obtain another one.

```shell-session
$ curl \
    --header "Authorization: Negotiate YIIFSw...sWw" \
    --request POST \
    --data '{"renewer": "yarn", "service": "openbao.example.com:8200"}' \
    https://openbao.example.com:8200/v1/auth/kerberos/delegation/token
```

- `renewer` names who may renew the token, usually the short name of the
  YARN ResourceManager principal. It is compared with the renewing
  principal's full name and, for callers from the owner's realm only, with
  its `primary/instance` and its primary alone.
  Without a renewer the token expires after one `renew_interval`.
- `service` is copied into the token's service field so the Hadoop client can
  find it in the job credentials; OpenBao does not interpret it.
- `max_lifetime` requests a shorter hard lifetime than the configured one.
- `role` selects the role as at login; without it exactly one role must match
  the principal. The role is fixed in the token record and is the one a later
  login uses.

The response carries the token in `token`, the Hadoop URL string form of
`Token` (`Token.decodeFromUrlString()` reads it), together with its owner,
renewer, dates and sequence number.

A holder logs in without SPNEGO:

```shell-session
$ bao write auth/kerberos/login delegation_token=KAARYWxpY2...
```

The OpenBao token carries the policies and parameters of the role recorded at
issuance, the entity alias is the token's owner, and `delegation_token` in
the metadata names the sequence number. Its explicit max TTL is capped by the
delegation token's remaining time to `expiry`, and it renews only while the
delegation token is still valid. Cancelling a delegation token does not revoke
OpenBao tokens already issued from it; they run out at their TTL.

`delegation/renew` and `delegation/cancel` take the token in `token`. Only the
renewer may renew, and the new `expiry` is `renew_interval` ahead, never past
`max_date`. The owner or the renewer may cancel; from then on the token fails
to log in or renew, which is how a job's tokens are retired when the
application finishes.

Tokens are signed with a random key that rotates every
`key_rotation_interval`; a key is kept while a token signed with it exists,
so rotation never breaks a live token. Every `cleanup_interval` the active
node deletes expired tokens and keys no token references. Deleting
`config/delegation` disables the feature and removes every token and key.

A delegation token is a bearer credential: transport it only over TLS and
treat job credential files as secrets.

## Authentication

From a client machine with a valid `krb5.conf` and `keytab`, perform a command
like the following:

```shell-session
$ bao login -method=kerberos \
    username=grace \
    service=HTTP/my-service \
    realm=MATRIX.LAN \
    keytab_path=/etc/krb5/krb5.keytab  \
    krb5conf_path=/etc/krb5.conf \
    disable_fast_negotiation=false
```

- `krb5conf_path` is the path to a valid `krb5.conf` file describing how to
  communicate with the Kerberos environment.
- `keytab_path` is the path to the `keytab` in which the entry lives for the
  entity authenticating to OpenBao. Keytab files should be protected from other
  users on a shared server using appropriate file permissions.
- `username` is the username for the entry _within_ the `keytab` to use for
  logging into Kerberos. With LDAP configured this username must match a
  service account in LDAP.
- `service` is the service principal name to use in obtaining a service ticket for
  gaining a SPNEGO token. It must belong to the `service_account` configured on
  the auth method.
- `realm` is the name of the Kerberos realm. With LDAP configured this realm
  must match the UPNDomain configured on the LDAP connection. This check is
  case-sensitive.
- `disable_fast_negotiation` is for disabling the Kerberos auth method's default
  of using FAST negotiation. FAST is a pre-authentication framework for Kerberos.
  It includes a mechanism for tunneling pre-authentication exchanges using armoured
  KDC messages. FAST provides increased resistance to passive password guessing attacks.
  Some common Kerberos implementations do not support FAST negotiation.
- `remove_instance_name` removes any instance names from a Kerberos service
  principal name when parsing the keytab file. For example when this is set to true,
  if a keytab has the service principal name `foo/localhost@example.com`, the CLI
  will strip the service principal name to just be `foo@example.com`.
- `role` is optional and only accepted when the auth method resolves policies
  through roles instead of LDAP. It restricts the login to the named role;
  without it exactly one role must match the principal.

## Troubleshooting

### Identify the malfunctioning piece

Once the malfunctioning piece of the journey is identified, you can focus
your debugging efforts in the most useful direction.

1. Use `ldapsearch` while logged into your machine hosting OpenBao to ensure
   your LDAP configuration is functional.
2. Authenticate to your domain server using `kinit`, your `keytab`, and your
   `krb5.conf`. Do this with both OpenBao's `keytab`, and any client `keytab` being
   used for logging in. This ensures your Kerberos network is working.
3. While logged into your client machine, verify you can reach OpenBao
   through the following command: `$ curl $VAULT_ADDR/v1/sys/health`.

### Build clear steps to reproduce the problem

If possible, make it easy for someone else to reproduce the problem who
is outside of your company. For instance, if you expect that you should
be able to login using a command like:

```shell-session
$ bao login -method=kerberos \
    username=my-name \
    service=HTTP/my-service \
    realm=EXAMPLE.COM \
    keytab_path=/etc/krb5/krb5.keytab  \
    krb5conf_path=/etc/krb5.conf
```

Then make sure you're ready to share the error output of that command, the
contents of the `krb5.conf` file, and [the entries listed](https://docs.oracle.com/cd/E19683-01/806-4078/6jd6cjs1q/index.html)
in the `keytab` file.

### Additional troubleshooting resources

- [The plugin's code](https://github.com/hashicorp/vault-plugin-auth-kerberos)

The OpenBao Kerberos library has a working integration test environment that
can be referenced as an example of a full Kerberos and LDAP environment.
It runs through Docker and can be started through either one of the following
commands:

```shell-session
$ make integration
$ make dev-env
```

These commands run variations of [a script](https://github.com/hashicorp/vault-plugin-auth-kerberos/blob/master/scripts/integration_env.sh)
that spins up a full environment, adds users, and executes a login from a
client.
